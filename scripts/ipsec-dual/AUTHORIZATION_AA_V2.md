# Experimental isolated native Authorization Authority V2

**Not enabled by default. No integration with `native.py`, supervisor admission, Java, or any packet gate. Not production-ready.** This component is an independently started Python HTTPS process; it never grants traffic. `NATIVE_DUAL_TUNNEL_STATUS` remains BLOCKED; `WEBSITE_UPDATE_READY` remains NO.

## Provisioning (all paths and host values explicit)

Use a separately administered host and private, persistent state directory (mode 0700), not the product checkout or `/run`. Provision a dedicated TLS CA, server certificate with SAN matching the configured endpoint, operator client certificate/key, node client certificate/key, and **separate** Ed25519 AA response-signing key. The node ID is the lowercase hex of the raw Ed25519 public key in the node TLS certificate. The node-pins JSON is `{ "<node-id>": "<sha256-of-node-cert-DER>" }`; operator pin is SHA-256 of operator cert DER, and operator-key-pin is lowercase raw Ed25519 operator public key hex (64 chars). Operator and node **public keys** must differ even if certificates have distinct fingerprints; startup rejects a configured operator-key-pin matching a node ID, and every authenticated operator transition checks its actual certificate public key against all node IDs and the configured pin. The trusted client CA validates their chains at TLS handshake; HTTP additionally verifies exact per-role fingerprint (and node key ID). Use dedicated PKIs and key permissions; tests generate only disposable keys in a private temporary directory. No production endpoint, PKI, trust, or credentials are supplied here.

```sh
/usr/bin/python3 scripts/ipsec-dual/authorization_aa_v2.py \
  --bind '<explicit-bind-address>' --port '<explicit-port>' \
  --db '<private-persistent-directory>/authority.sqlite' \
  --signing-key '<private>/aa-ed25519.pem' \
  --server-cert '<private>/server.pem' --server-key '<private>/server-key.pem' \
  --client-ca '<private>/clients-ca.pem' \
  --node-pins '<private>/node-pins.json' \
  --operator-pin '<64-lowercase-hex-cert-sha256>' \
  --operator-key-pin '<64-lowercase-hex-raw-Ed25519-public-key>' \
  --max-workers 32 --max-issuances 100000
```

Requires Python `cryptography` plus stdlib `ssl`/`sqlite3`. Use an absolute, non-symlinked state directory owned by the AA process UID with mode 0700; the database is reserved exclusively at mode 0600 before SQLite opens it, and must still be 0600 on restart. Start with no existing DB for bootstrap. A pre-existing DB **always starts quarantined**, even after clean shutdown; corruption fails startup. The AA creates private `authority.sqlite.pristine` and `authority.sqlite.used` sidecars in that directory; persist them with the DB and never delete, reset, or restore them independently. Persistently protect signing keys and CA material separately from the state DB. Do not mount them into endpoints.

## API and state transitions

`POST /v2/authorization/transition` requires operator mTLS certificate + exact operator pin. JSON fields exactly `{version:2,nodeId,scope,generation,revocation,epoch,action}`. `nodeId` is 64 lowercase hex; `scope` is 1–128 ASCII letters/digits/dot/underscore/hyphen; numeric fields are positive signed-63-bit except nonnegative revocation. Actions:

- `authorize`: generation strictly rises; revocation cannot decrease; epoch strictly rises. Initial authorization is operator initiated. All previous issuance IDs become invalid.
- `revoke`: generation cannot decrease; revocation strictly rises; epoch strictly rises; all previous issuance IDs become invalid and attestations are denied.
- `recover`: only in quarantine with an existing scope; supplied generation and revocation at least as high as stored and epoch strictly higher. For a clean start-stop-start with **no scopes, challenges, or issuances**, a fresh operator-pinned `recover` can instead establish a denied scope only if the locally persisted private pristine sidecar still reads `fresh` and no used marker exists; unrecognized legacy empty DBs cannot use this path. Recovery marks local history used and revokes previous issuance IDs before acknowledgment, clears quarantine atomically under the same authority lock after durable commit (so a later fsync failure cannot be overwritten), but does **not** authorize. A separate newer operator `authorize` is required. Operators must compare to **independently held** floors before recovering. Without an independent anchor, this is a procedural control, not proof against rollback.

`POST /v2/authorization/attest` requires node mTLS cert, exact pinned cert fingerprint, and node ID matching its Ed25519 public key. Request fields exactly `{version:2,nodeId,scope,challenge,bootId,sessionId,lastObservedGeneration}`. Challenge, boot and session IDs are each 32 lowercase random hex chars (generate with `secrets.token_hex(16)`); challenge MUST be generated freshly per request. Authorized scope only. A local observed generation above stored generation quarantines the service. Reused `(node,scope,challenge)` is denied, including after restart. A successful response is `{payload,signature}`, where the payload consists in this exact canonical order: `version,nodeId,scope,challenge,bootId,sessionId,epoch,generation,revocation,issuanceId,issuedAtMs,expiresAtMs`. Signature is canonical base64 Ed25519 over ASCII `DEFENDERLINK-NATIVE-AA-ATTEST-V2\n` followed by `key=value\n` lines in that order. 30-second bounded wall-clock validity; each 128-bit issuance ID is persisted with validity and revoked by every scope transition. An already issued response cannot be retrospectively recalled at a disconnected verifier: re-attest and compare authoritative floors for current status. No grant should be inferred solely from this helper.

`AttestationVerifier` pins **AA response public key separately from TLS CA**, node ID, scope, and caller-provided generation/revocation/epoch floors. `challenge(request)` binds the pending boot/session/challenge and observed generation; `accept(response)` checks schema, signature, exact binding, floors, wall clock (5s early skew maximum), issuance replay and expiry, then consumes pending challenge and advances floors. Both methods serialize pending/replay/floor changes with one lock so concurrent acceptance cannot consume one issuance twice. An invalid response never grants; on restart reconstruct from independently trusted floors and issue a fresh challenge. The optional `request_attestation(explicit_https_url, ca_path, node_cert_path, node_key_path, request, verifier)` uses hostname-checked mTLS, bounded read/timeout, and returns False on unavailable/invalid/rejected service. It is **not** wired to native traffic.

## Durability and limits

SQLite connection uses `journal_mode=DELETE`, `synchronous=FULL`, `BEGIN IMMEDIATE`, unique challenge/issuance constraints, then SQL `COMMIT`, then explicit `fsync` of the DB inode and its parent directory **before** sending transition acknowledgment or signing/returning an attestation. SQLite FULL syncs its rollback journal before applying database writes and the DB before commit. For new DB, schema creation completes and file/directory are synced before serving. The pristine sidecar is changed to `used!` and a used sidecar is fsynced before the first scope commit; a DB-only rewind to an empty snapshot is therefore refused during restart recovery. Commit or fsync uncertainty quarantines the process; an in-progress transaction is rolled back on error. Changes to high-water and revocation invalidate issuance IDs within the same transaction. Atomicity and fsync depend on actual filesystem/storage flush guarantees; this code cannot certify hardware persistence. TLS handshakes run in daemon workers after plain TCP accept with a 2-second socket timeout; header parsing has a separate 2-second total deadline so a trusted but unpinned certificate cannot trickle lines indefinitely. Concurrent worker slots are capped at 32 by default (`--max-workers`, 1–256), reserved nonblocking before thread creation and released on worker completion. Excess TCP clients are closed before TLS; there is no guaranteed availability under floods or OS-level accept backlog pressure. Authenticated POST bodies are limited to 4096 bytes and a 2-second total read deadline, with incomplete/late bodies denied. Persisted challenge and issuance rows each have an explicit lifetime quota of 100000 by default (`--max-issuances`, 1–1000000), checked inside the issuance transaction before either insertion; when either reaches quota, new attestation returns 503 without consuming a challenge or pruning replay history. Issuance ceases until separately designed, externally anchored archival/migration; increasing the quota is not an unbounded retention strategy, and storage can still be exhausted earlier by the OS.

**Whole-authority storage rollback remains detectable only with an independent monotonic anchor.** DB-only rollback to a pristine empty snapshot is blocked by surviving local sidecars, but restoring or forging the entire DB **and sidecars** can erase high-water and evidence; SQLite, fsync and local markers cannot identify that state. Startup quarantine requires explicit operator recovery plus a new authorization, but an operator who supplies floors from that same rolled-back DB can still accept old history. Until externally protected monotonic floors, recovery authentication/procedures and independent host/storage are provisioned and validated, do not label this production PASS. Service unavailability, wrong cert/key, ambiguous state, and invalid attestation are deny-only. No packet enforcement is implemented here.
