# Standalone native issuance V2 foundation (NOT enabled)

The deployed `NATIVE_DUAL` operator path **always denies**. Scheduled `NativePolicyExporter.refresh()` publishes only `allowed:false` legacy compatibility records; the operator supervisor ignores even those. Neither this foundation nor an Ed25519 signature constitutes a packet-time admission gate.

## Canonical signature contract

Payload fields, in strict order: `version` (integer 2), `transport` (`IKEV2_ESP_WIREGUARD`), `serviceId` (1–128 ASCII letters/digits/`.`/`_`/`-`), `clientNodeId` and `ownerNodeId` (64 lowercase hex, raw Ed25519 public keys), `bootId` (lowercase UUID spelling), `nonce` (32 lowercase hex), `generation`, `issuedBoottimeNs`, `deadlineBoottimeNs` (positive signed 64-bit decimal integers), `resource` (pinned `tcp:IPv4:port` string), `issuanceId` (32 lowercase hex) and `issuerId` (64 lowercase hex of the separately pinned operator public key). Extra/missing fields, noncanonical base64, bool-as-int, bad signatures, invalid scope and invalid lifetimes deny. Lifetime is at most 3 seconds; deadline is the **original absolute CLOCK_BOOTTIME** value, never recalculated on restart or delayed installation.

The operator signs ASCII bytes `DEFENDERLINK-NATIVE-ISSUANCE-V2\n` followed by `key=value\n` for every payload field in the order above. The node countersigns `DEFENDERLINK-NATIVE-NODE-V2\n` + those exact bytes + the 64 raw bytes of the operator signature. Both signatures are standard Ed25519, base64-encoded in a JSON object `{ "payload": ..., "operatorSignature": ..., "nodeSignature": ... }`. The pinned operator public key must be provisioned separately from the node key; no key material or automatic key generation is in this protocol. Python uses `cryptography` (install in an isolated environment); Java uses existing Bouncy Castle verification via `NodeIdentity.verify` and an explicitly supplied signer.

`NativeIssuanceV2` requires independently configured service/client/resource scope and distinct pinned Ed25519 keys; `expect(bootId, nonce)` records only caller-supplied values. `issue(...)` verifies an explicitly signed operator approval, owner and issuer key IDs, scope, generation and the supplied trusted receiver BOOTTIME, consumes the challenge, verifies its own countersignature and returns an envelope. `ChallengeVerifier` independently checks both signatures, exact caller-supplied scope/boot ID, nonce, generation floor and original deadline and consumes the nonce. Both objects are **standalone primitives**, not a connected issuance workflow. Neither object itself samples `CLOCK_BOOTTIME`, reads the actual boot ID, generates a nonce, persists a high-water mark, or authenticates the caller. The missing control path must do all of those and pin the operator public key out-of-band. Never infer operator approval from a ledger snapshot or re-sign materialized state. A receiver restart requires a new unpredictable in-memory challenge; a reboot requires a new boot ID. Do not issue from scheduled ledger refresh. A JUnit fixture now produces a Java-signed envelope and passes it to the real Python `cryptography` verifier, but both keys and the challenge are synthetic; this is cryptographic wire compatibility, not a running exporter/supervisor integration.

## Blocked acceptance gates

1. No authenticated post-boot operator approval/control channel, independently pinned production operator key, or durable revocation/generation authority is wired. `NodeIdentity` now enforces private file creation and consistency, but its same-UID pathname threat limit remains; these standalone classes do not establish a production issuer. The current isolated native Dockerfile installs Python but not `cryptography`, so the verifier is **not available in that image** until explicitly packaged and tested.
2. No independent default-deny kernel classifier enforcing the original `CLOCK_BOOTTIME` deadline at **packet time**, across established flows, crashes, rollback, restart and reboot. Existing lab-only nft `meta time`/timeout commands are wall-clock based and cannot implement this gate. **Do not route a standalone verifier result into `Topology.authorize`** or claim native packet acceptance.
3. No genuine ledger-operation owner-signature verification or Merkle payload coverage; materialized records cannot authorize an issuance automatically. Existing tests using unsigned fixture ledger operations demonstrate only denial.
4. No packet-level namespace or pfSense interoperability acceptance is established by unit tests. Keep host networking and website untouched.

Tests: `mvn -q -Dtest=NativeIssuanceV2Test,NativePolicyExporterTest test`; from `scripts/ipsec-dual`, run an isolated Python with `cryptography` installed: `python -m unittest test_issuance_v2 test_native`.
